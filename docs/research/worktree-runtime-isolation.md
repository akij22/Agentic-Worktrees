# Provider runtime isolation mechanics

Research resolution for [Wayfinder #58](https://github.com/akij22/agentic-worktrees/issues/58), part of #57. Research only; no application changes or claim of an approved implementation specification.

## Answer

Use a main-process registry owning **one lazily started provider process per `(agentKind, worktreeId)`**, shared by that worktree's sessions, with stable private provider state, an immutable assigned-Skill projection, and a serialized lifecycle. This removes the current provider-wide restart and catalog mutation boundary. **A separate process, CWD, or extra Skill directory alone does not establish an exclusive catalog.** Both providers inherit other discovery/configuration sources. Catalog enforcement must suppress or deny unassigned sources and verify the effective provider catalog before allowing turns; otherwise fail closed. [R1–R4, C1, O1]

The source establishes restart/resume feasibility, not a turnkey strict-isolation recipe. In particular, the installed OpenCode release adds a built-in Skill and the repository emits an incompatible Skill configuration shape. These are implementation gates, not reasons to silently weaken “new worktrees begin empty.” [R4, O1]

## What the application actually owns today

| Concern | Committed behavior and consequence |
| --- | --- |
| Ownership | `coding-agent-service.ts` has one harness/adapter per provider kind, not per worktree. Startup promises are keyed by kind. A single global Skill catalog is fanned out to both adapters. [R1] |
| Managed Skills | `SkillService` and the installer maintain a shared `<userData>/skills/active/<id>/SKILL.md` projection. Application wiring passes `{ activeRoot, expectedIds }`, with no worktree identity. This implements the older globally available Skills design, not #57's assignment boundary. [R5] |
| Codex | One `codex app-server` child, JSONL over stdin/stdout. Adapter maps thread IDs to directories, snapshots, turns, approvals, and capability connections. `thread/start` is non-ephemeral; `thread/resume` uses the persisted external ID and CWD. [R2, R3] |
| OpenCode | One authenticated `serve --hostname 127.0.0.1 --port …` child; directory-scoped HTTP requests and a global SSE subscription. The child inherits the parent environment, adding server authentication and `OPENCODE_CONFIG_CONTENT`; it is not given a private provider home/data namespace. [R4] |
| Skill verification | Codex calls `skills/extraRoots/set`, then `skills/list({ cwds: [directory], forceReload: true })`; it requires exactly the expected **enabled** names and managed paths. OpenCode restarts for changed catalogs and compares **all returned** Skill names/locations to the managed projection. Neither comparison itself removes ambient Skills. [R2, R4] |
| MCP reconfiguration | Both adapters restart their shared provider. Codex requires all supplied sessions idle, restarts, resumes each thread with `config.mcp_servers`, then verifies tools; OpenCode waits for idle, restarts with new config, re-reads sessions, then verifies MCP status/config/tool IDs. Both attempt rollback. Therefore a change currently crosses worktrees using the same provider. [R2, R4] |
| Coordination | Capability reload/session reads are queued per provider installation. Global Skill synchronization blocks sends, but startup promises do not serialize Skill configuration, restart, and shutdown into one lifecycle transaction. [R1] |
| Routing | Adapter events are matched from external session IDs to persisted runs; server/unknown events can have no run ID. A multi-runtime design must bind events and failures to their owning runtime, not broadcast a provider-wide failure. [R1] |
| Shutdown | Codex rejects pending requests and uses SIGTERM, a one-second wait, SIGKILL, then another bounded wait. OpenCode aborts SSE, clears clients, sends SIGTERM and escalates after two seconds; its race can return after sending SIGKILL without confirming exit. Electron waits for service shutdown with `Promise.allSettled`. This is a starting point, not proof that descendants are reaped. [R3, R4, R6] |

## Codex: available isolation mechanisms

**Discovery scope.** Pinned `resolve_skill_roots_with_home_dir` begins with configuration-layer roots, then extends them with plugin roots, extra roots, and repository `.agents/skills` roots. User roots include both the legacy `CODEX_HOME` Skill location and the user's `.agents/skills`; system/admin roots also exist. Thus `skills/extraRoots/set({ extraRoots: [projection] })` replaces only the extra-root list, not all native discovery. Changing `CODEX_HOME` alone cannot remove repository, home, system, or plugin discoveries. [C1]

**Observed protocol.** Generated 0.153.4 types expose:

- `SkillsExtraRootsSetParams = { extraRoots: AbsolutePathBuf[] }`;
- `SkillsListParams = { cwds?: string[]; forceReload?: boolean }` (empty CWD list defaults to session CWD);
- `SkillsConfigWriteParams = { path?: AbsolutePathBuf | null; name?: string | null; enabled: boolean }`;
- `thread/resume` with `threadId`, optional `cwd`, configuration overrides, and optional runtime workspace roots;
- `config/mcpServer/reload`, with no parameters, and `mcpServerStatus/list`.

Per-Skill enablement is a candidate enforcement mechanism, **not a documented universal root allowlist**. Treat process-level extra roots/configuration as runtime-owned, not session-owned; validate every effective CWD used by that runtime. `forceReload` bypasses catalog cache; `skills/changed` and upstream watcher behavior mean verification is not a permanent guarantee against later filesystem changes. [C1–C3]

**Resume.** The protocol explicitly supports disk-backed resume by thread ID; history/path alternatives exist but are marked unstable. For an already running thread it rejoins the thread rather than promising a fresh reconfiguration. The existing adapter's idle stop/start/resume sequence is therefore a better established baseline than assuming a resume call atomically replaces a live thread's environment. Keep the original durable provider namespace across idle eviction/crash restart; creating a fresh home each spawn would invalidate the assumption that an external ID remains resolvable. Codex resolves `CODEX_HOME` as a configuration/authentication namespace as well, so changing it is not merely a Skill-path setting. [C3, C4, R2]

**MCP.** The installed protocol has a reload request, but the committed adapter does not use it. Availability of a method is not evidence of atomic per-worktree Skill-and-MCP activation or rollback. Start with the existing restart/resume/verify strategy, confined to the owning runtime; require separate version-specific tests before substituting live reload. [R2, C3]

## OpenCode: available isolation mechanisms

**Discovery scope and cache.** The pinned Skill implementation uses `InstanceState` for discovery and loaded Skills. It scans external `.claude` and `.agents` directories in home and from the requested directory up to the worktree, configuration directories' `skill`/`skills` trees, configured `skills.paths`, and `skills.urls`. This is additive. Directory-scoped state is useful, but does not isolate process-wide environment, shared config/storage, or restart failure. [O1, O2]

**Two concrete compatibility constraints.** The repository currently serializes `skills: [root]`; both the installed SDK and upstream loader expect `skills: { paths: [root] }`. Also, OpenCode 1.18.30 registers `customize-opencode` at location `<built-in>` before disk discovery. `Skill.all()` returns the full state, while `Skill.available(agent)` filters names using the agent's Skill permissions. A strict managed-path comparison must account for which surface it measures: raw discovery and agent-accessible Skills are different sets. Merely excluding the built-in from the application's display would not enforce isolation. [R4, O1]

**Suppression and enforcement.** Version 1.18.30 exposes `OPENCODE_DISABLE_EXTERNAL_SKILLS`, `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS`, and the separate `OPENCODE_DISABLE_PROJECT_CONFIG` control. Even disabling external scanning leaves configuration roots, configured paths/URLs, and the built-in. A private config directory is not itself a replace-all switch. [O5] A candidate configuration must control every source and apply Skill permissions consistently to all selectable agents and explicit invocation paths. Prove both automatic availability and explicit denial, not just a raw `/skill` listing. [O1, O2]

**Persistence.** Session rows retain their directory and workspace identity; directory-filtered requests are not separate databases. Global data/config/cache/state paths derive from XDG-based locations. Keep a stable namespace across restarts and verify platform-specific environment overrides before relying on them for isolation. Changing the namespace requires deliberate migration of old sessions and authentication. [O6]

**MCP and disposal.** MCP clients/tool definitions are instance state; upstream closes clients during replacement/disposal. The official server API exposes `POST /instance/dispose` (not session deletion), plus MCP status/add/connect/disconnect operations. That gives a potential lighter reconfiguration boundary, but no evidence here establishes an atomic Skill-plus-MCP transaction or revocation of already loaded session instructions. The repository already uses process restart and persistent session reattachment; retain that conservative baseline until dynamic mutation is proven for the supported version. [O3, O4, R4]

## Constraints for the runtime-registry decision

The following are **recommendations derived from the evidence**, not descriptions of implemented behavior:

1. **Identity and ownership:** registry key `(agentKind, worktreeId)` with a main-process-resolved canonical worktree path. Each entry owns child PID/transport, startup promise, subscriptions, pending requests/approvals, session mappings, installed-provider version, assignment generation, and lifecycle state. A stale callback must carry a generation token and cannot mutate a replacement runtime.
2. **Stable disk namespace, ephemeral process:** use durable `<runtimeState>/<provider>/<worktreeId>` state and immutable generation-specific Skill projections. Preserve provider session storage on idle eviction and restart. Credentials must be deliberately provisioned through the backend's supported auth/environment mechanism; do not blindly copy a user's entire provider home/config or expose secrets to IPC/logs. Existing sessions in a previously shared namespace need an explicit migration/reconciliation strategy before switching homes.
3. **One serialized lifecycle per key:** start, apply assignments, crash recovery, idle eviction, and stop share the same queue/state machine. Quiesce all sessions of the affected worktree, including pending permissions/aborts; do not block unrelated worktrees. Recheck idleness under the admission gate to avoid a send/restart race.
4. **Coherent activation:** prepare a candidate Skill projection and MCP profile; restart the affected runtime; reattach/verify its session IDs, effective enabled Skill names **and canonical paths**, and expected MCP tool set; only then publish the applied generation and admit turns. Keep the previous projection/config alive for rollback. If activation or rollback cannot be verified, expose Failed/unavailable, not Enabled.
5. **Scope of isolation:** assignment isolation means provider-discoverable/invocable Skills, not an OS sandbox preventing every file read. Instructions already in session history cannot be “unloaded” by deleting a Skill root. The specification must define what removal promises for resumed conversations; do not imply that historical knowledge is erased.
6. **Bound resources:** lazy start; configurable global and per-provider process limits; evict only idle, unleased least-recently-used runtimes after an idle TTL. If all slots are busy, queue or return explicit capacity status rather than terminating an active run. Include provider descendants, MCP hosts, SSE streams, memory, and pending-request limits in the budget. Numeric limits require measurements; this research establishes none.
7. **Recovery and events:** persist external session IDs with provider/worktree identity and applied generation. Route events by runtime key plus external session ID; server exit affects only its owned runs. Retry with a bounded policy; never silently create a fresh conversation when resume fails.
8. **Shutdown:** close admission, cancel/drain turns under a deadline, resolve/reject pending approvals/requests, dispose OpenCode instance clients where safe, abort streams, terminate only owned children, and wait for actual exit after escalation. Verify descendant ownership/cleanup rather than using broad process-name kills. Retain durable session state.

## Unknowns and acceptance gates

- **Strict catalog enforcement remains a proof obligation.** No inspected API replaces every Codex discovery root; OpenCode contains an unconditional built-in in raw discovery. Decide whether “empty” means zero usable assigned Skills or literally zero raw catalog entries. Under a literal raw-empty requirement, the inspected OpenCode implementation cannot satisfy it without a provider change. Do not silently reinterpret the product requirement.
- Validate a version-pinned Codex disabled-Skill policy and OpenCode deny-by-default policy against all automatic/explicit entry points, plugins, ambient project/home/admin roots, duplicate names, CWD changes, and filesystem watcher reloads. Permission denial and discovery absence are not interchangeable evidence.
- Confirm durable storage/auth namespace behavior and migration for existing sessions before isolating provider homes or XDG paths. A resumable ID is not a portable session export.
- Determine whether hot MCP reload or instance disposal can replace process restart without stale tools, stale Skill caches, or historical instruction surprises. Until tested, no atomicity claim is justified.
- Run real-provider smoke tests: two worktrees with disjoint Skills; an empty worktree; simultaneous turns; assignment changes while busy/waiting permission; one runtime crash while the other continues; idle eviction/resume; failed activation/rollback; and app exit with owned descendants. Verify native catalogs, invocation failures, session continuity, event routing, and process counts—not renderer filtering alone.
