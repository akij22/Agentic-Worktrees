## Contract and lifecycle

Removal is a two-call, single-consent-lease operation. Inspection returns the immutable, path-free tuple `(inspectionId, packageName, capabilityId, activeVersion, activeIntegrity, activeContentDigest, activeRunCount, expiresAt)`. Acceptance must repeat the exact inspection ID, package name, active version, and active-run count. The global `PackageLock` remains owned across inspection, consent, validation, deactivation, commit, rollback/recovery, cleanup, and terminal release.

Before mutation, removal verifies a managed installed Capability, catalog identity, exact installation/configuration/session snapshots, and idle active runs. It deactivates all reviewed active runs, detaches the pointer reversibly, atomically removes the installation/configuration, refreshes the catalog, and stages only unreferenced version directories for garbage collection. Successful removal never auto-activates a session.

The durable removal-recovery row contains relative/serializable snapshots and GC digests. Pointer, database, catalog, GC, or runtime failure restores the exact pointer, installation, configuration, settings, sessions, and staged versions. Conflicting restoration is quarantined rather than overwriting external state. Secret references and chat associations remain through rollback; secrets are deleted only during successful cleanup. Cleanup failure remains `cleanup_pending` and startup reconciliation retries it without activation.
